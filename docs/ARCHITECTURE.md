# Notebook Scanner: feasibility and decision

Researched 18 October 2026. **Conditional go for a hardware experiment with Bluetooth Classic RFCOMM.** Documentation establishes compatible APIs, not reliability on your particular Bluetooth adapters. Do not build a polished installer, remote camera control, or alternative transports until the experiment passes.

Follow-up: the user confirmed capture-to-paste on their Samsung S23 without Wi-Fi and found transfer speed acceptable. Version 0.2 therefore keeps the transport and focuses on remembered devices and app-open reconnection; see [connection UX and its sources](CONNECTION-UX.md). The original hardware path is demonstrated, while the new automatic setup behavior still requires a device trial.

Version 0.3 adds [the automatic standard-camera shortcut](CAMERA-SHORTCUT.md), Camera/Settings tabs and last-successful-device restoration. Following the user's clarification, the existing phone camera and its lens selection are retained. No direct camera permission or new camera SDK is introduced.

## What this actually promises

Android takes a notebook photo; a small native Android app compresses it and sends it to a native Windows app. Windows puts an image on its clipboard. You choose the destination and press Ctrl+V. Neither app controls a browser, sends a ChatGPT message, performs OCR, or calls an online API. Transfer can work with Wi-Fi and mobile data disabled. Loading ChatGPT or submitting the image later still needs that service's connectivity; this utility cannot make ChatGPT itself offline.

The linked conversation was retrieved, but its earlier assistant messages were opaque content references, not readable explanations. The following challenges the assumptions in the requested plan; it does not claim to quote the previous assistant.

## Transport comparison

| Option | Offline and setup | Photo transfer / engineering cost | Decision |
| --- | --- | --- | --- |
| Classic RFCOMM | Bluetooth radios only; pair once in OS settings, select the paired peer in each app | Ordered byte stream on both platforms; ordinary framing, checksum, disconnect handling. Still need to measure real throughput | First experiment |
| BLE GATT | Bluetooth only; discover a custom service, choose central/peripheral roles, establish trust | Fragment into characteristic-sized writes/notifications; negotiate MTU, handle queues, backpressure and completion. Battery advantage has little value for occasional foreground photos | Reject for first version |
| BLE LE L2CAP CoC | Android has public secure LE channel APIs from API 29; dynamic PSM must also be exchanged | Attractive stream semantics on Android, but the reviewed Windows application API surface documents GATT/RFCOMM, not an equivalent general LE CoC socket. Driver-level L2CAP is not evidence of a usable .NET API | No-go unless a supported Windows user-mode API is demonstrated; no custom driver |
| Wi-Fi Direct | Needs Wi-Fi hardware enabled, but no router or internet | IP sockets make large photos easier; peer discovery, group ownership, Windows pairing/driver behavior and Android permissions add complexity | Fallback investigation if Bluetooth speed fails |
| Android local-only hotspot | Android creates an offline WLAN; user joins its SSID from Windows | Conventional TCP/HTTP, potentially much faster. Adds joining/leaving networks, authentication, address discovery and firewall considerations | Simplest Wi-Fi fallback; not implemented |

Microsoft recommends GATT for low-bandwidth/power-sensitive work and describes RFCOMM as a bidirectional serial-style socket; it also confirms desktop access and recommends pairing for lasting trust. This supports RFCOMM as a candidate, not a measured speed guarantee. [Windows Bluetooth FAQ](https://learn.microsoft.com/en-us/windows/apps/develop/devices-sensors/bluetooth-dev-faq).

Android's RFCOMM server registers a UUID through SDP; the matching client discovers the channel. Secure server sockets require authentication/encryption. We choose **Android server, Windows client** so the phone handles service registration and the desktop does not need an advertising listener or hand-written SDP record. The server only accepts the laptop explicitly selected from bonded devices. [Android connections](https://developer.android.com/develop/connectivity/bluetooth/connect-bluetooth-devices), [BluetoothAdapter API](https://developer.android.com/reference/android/bluetooth/BluetoothAdapter).

For LE, Android explicitly exposes `createL2capChannel` and says applications must obtain the dynamic PSM. Windows' documented app BLE surface is GATT/GAP; Windows driver L2CAP documentation concerns profile drivers. **The conclusion about LE CoC is a scope decision based on the reviewed APIs, not a claim that Windows has no L2CAP internally.** [Android BluetoothDevice](https://developer.android.com/reference/android/bluetooth/BluetoothDevice), [Windows BLE overview](https://learn.microsoft.com/en-us/windows/uwp/devices-sensors/bluetooth-low-energy-overview), [Windows L2CAP profile drivers](https://learn.microsoft.com/en-us/windows-hardware/drivers/bluetooth/accepting-l2cap-connections-in-a-bluetooth-profile-driver).

Wi-Fi Direct avoids an access point, but Android requires discovery/connection permissions and still declares `INTERNET` for Java sockets even when the traffic is entirely local. Modern Android targets use `NEARBY_WIFI_DEVICES`; older discovery paths involve location permission/settings. The legacy Windows desktop route requires prior Windows pairing. Windows also offers WinRT group-owner/legacy access-point APIs, whose availability still depends on hardware/drivers; this is not an automatic cross-platform connection. [Android Wi-Fi P2P](https://developer.android.com/develop/connectivity/wifi/wifip2p), [Windows desktop Wi-Fi Direct](https://learn.microsoft.com/en-us/windows/win32/nativewifi/about-the-wi-fi-direct-api), [Windows Wi-Fi Direct driver/API guidance](https://learn.microsoft.com/en-us/windows-hardware/drivers/partnerapps/wi-fi-direct).

Android local-only hotspots explicitly have no internet access and expose a reservation with network credentials. Android 13+ targets need nearby Wi-Fi permission; older paths require location. A Windows user can join the resulting WLAN conventionally, avoiding Android-to-Windows Wi-Fi Direct negotiation. It still violates a literal requirement that Wi-Fi remain off. Use a per-session authenticated/encrypted application channel if this fallback is built; being on a hotspot alone is not application authorization. [Local-only hotspot](https://developer.android.com/develop/connectivity/wifi/localonlyhotspot).

## Speed: no claim of instant transfer

Bluetooth SIG lists Classic PHY rates of 1–3 Mb/s and ordinary LE PHY rates up to 2 Mb/s. These are **radio rates, not JPEG throughput**. Protocol overhead, Windows drivers, congestion, retransmissions and connection setup all reduce usable speed. BLE 2M availability does not imply a fast GATT file-transfer implementation. [Bluetooth technology overview](https://www.bluetooth.com/learn-about-bluetooth/tech-overview/).

Illustrative arithmetic, not benchmarks: a 1 MiB image contains about 8.39 megabits. At measured application throughput of 0.2, 0.5 or 1 Mb/s, payload alone would take about 42, 17 or 8.4 seconds. A 300 KiB image at 0.5 Mb/s needs about 4.9 seconds. Even an ideal 3 Mb/s radio needs about 2.8 seconds for 1 MiB before overhead.

The experiment re-encodes to JPEG quality 85 and a maximum 2400-pixel long edge. This is a **starting quality tradeoff**, not proven sufficient for small handwriting. It may still produce a multi-megabyte photo. We must test legibility before tuning compression. Proposed acceptance target: median capture-confirmation-to-clipboard under 10 seconds, 95th percentile under 20 seconds, and readable smallest writing. These are product gates, not predictions. Both apps reject payloads above 8 MiB; a frame gets a 120-second deadline.

## Permissions, camera and lifecycle

Minimum Android version in this experiment: Android 9/API 28, for `ImageDecoder`; this is a scope choice rather than a Bluetooth requirement. Android 12+ requests runtime `BLUETOOTH_CONNECT` (Nearby devices). Older versions declare legacy `BLUETOOTH` through API 30. We deliberately use OS settings for pairing and select already bonded peers: no in-app scan, no `BLUETOOTH_SCAN`, no location permission, no discoverability request. If discovery is added later, the permission matrix changes. [Android Bluetooth permissions](https://developer.android.com/develop/connectivity/bluetooth/bt-permissions).

The phone delegates capture to the system camera with `ACTION_IMAGE_CAPTURE`, a private-cache file and a narrowly scoped FileProvider URI grant. This uses a real output file, not the thumbnail in the result intent. The app does not request direct camera or broad photo-library access. `ImageDecoder` scales before allocating the output; re-encoding removes source EXIF metadata. Test orientation on real cameras. [Camera intent guide](https://developer.android.com/media/camera/camera-deprecated/photobasics), [ImageDecoder](https://developer.android.com/reference/android/graphics/ImageDecoder).

There is **no always-on service**. Both apps must be opened, and the phone must remain unlocked during a session. The transport thread may survive while the system camera is on top, but Android can kill that process; the app then requires reconnecting and retaking the photo. Orientation changes are handled without Activity recreation, but process death is not hidden. A production transfer that must survive backgrounding needs an appropriately declared `connectedDevice` foreground service or a companion-device approach, including modern foreground-service start restrictions and user-visible lifecycle. [Android Bluetooth background guidance](https://developer.android.com/develop/connectivity/bluetooth/ble/background).

Do not promise that a desktop button will launch a closed phone app's camera. Android restricts background Activity launches. A later remote trigger can reasonably operate while the app is already visibly open; waking a locked/closed phone is a different feature with a substantially worse permission/lifecycle burden. [Android background Activity restrictions](https://developer.android.com/guide/components/activities/secure-bal).

## Windows implementation and clipboard

Use C# WinForms for a small ordinary desktop window and its STA clipboard API. Use OS WinRT `BluetoothDevice`, `RfcommDeviceService` and `StreamSocket` through a Windows-targeted .NET project. Microsoft's guidance supports Windows-specific TFMs without installing Windows App SDK/WinUI. Do not add MAUI, Electron, a web server, COM-port configuration, 32feet or a custom driver. Android uses Java and a small AndroidX FileProvider dependency, without Kotlin/Compose/CameraX for this test. [Calling WinRT from desktop .NET](https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/winrt-apis-desktop-apps).

Windows enumerates bonded devices, queries the exact custom UUID uncached, and connects with `BluetoothEncryptionWithAuthentication`. Consent dialogs may appear; the first hardware test must establish unpackaged-desktop consent behavior on the target PC. Packaged Windows apps declare the Bluetooth capability. Do not assume UWP sample packaging instructions apply unchanged to an unpackaged WinForms EXE. If the hardware trial exposes a packaging requirement, evaluate MSIX explicitly rather than silently demanding developer mode. [Windows RFCOMM API and sample](https://learn.microsoft.com/en-us/windows/apps/develop/devices-sensors/send-or-receive-files-with-rfcomm), [RfcommDeviceService contract](https://learn.microsoft.com/en-us/uwp/api/windows.devices.bluetooth.rfcomm.rfcommdeviceservice).

The receiver verifies length, SHA-256 and JPEG header dimensions, decodes the image and copies a persistent Windows bitmap to the clipboard. It retries a temporarily busy clipboard before acknowledging success. Only then does Android report “Copied.” Ctrl+V is manual. Clipboard support in a particular ChatGPT browser/app build is an **acceptance test**, not established by Bluetooth documentation. The local-JPEG test isolates this before touching radio code. Use Android's send/ack measurement for transfer speed and a stopwatch for the entire capture flow; version 0.2 removes the Windows idle-inclusive timing label.

## Existing capabilities: try before overbuilding

* **Windows Bluetooth file transfer:** built in, offline, and worth using as a baseline with an existing photo. It requires entering Receive files and later saving the file, rather than continuously populating the clipboard. It might already be good enough if automation is not worth maintaining. [Microsoft file transfer instructions](https://support.microsoft.com/en-us/windows/hardware/bluetooth/send-and-receive-files-over-bluetooth-in-windows).
* **Phone Link / Link to Windows:** photo access and cross-device clipboard are relevant, but not a general account-free, Bluetooth-only solution. Android setup requires a Microsoft account and normally the same Wi-Fi network; feature support varies by phone. Current Windows 11 guidance also moves photo browsing into File Explorer. [Setup requirements](https://support.microsoft.com/en-us/windows/apps/phonelink/phone-link-requirements-and-setup), [Photo feature changes](https://support.microsoft.com/en-us/windows/apps/phonelink/setting-up-photos-in-the-phone-link).
* **Quick Share:** established Android/Windows file sharing deserves consideration if “no internet” permits Wi-Fi radios. Google's instructions require Wi-Fi and Bluetooth enabled and document network restrictions. It is not our strict Bluetooth-only clipboard workflow. Do not describe it as requiring internet for every transfer, or as automatically filling a clipboard. [Google Quick Share requirements](https://support.google.com/android/answer/13801258?hl=en).

## Security and privacy boundary

OS pairing is necessary but not sufficient authorization: Android only accepts the selected bonded address; Windows connects to the chosen bonded phone and custom service. Verify pairing codes on both screens. The UUID is an identifier, not a secret. We request authenticated encrypted RFCOMM on both ends, never insecure sockets or an encryption fallback. SHA-256 detects framing/data errors; it is not a MAC or substitute for authenticated Bluetooth.

No ads, telemetry, accounts, HTTP server, or internet permission in the Android app. One image is in flight; explicit capture sends it automatically. Raw captures are app-cache files deleted after preparation/cancel, with startup cleanup after interrupted runs. Cameras/OS caches may have their own retention. The receiver keeps data in memory and on the ordinary Windows clipboard. Other local apps and user-enabled clipboard history/sync may retain or read it; this prototype does not override those settings or claim end-to-end confidentiality through ChatGPT. Clipboard contents are replaced on each successful photo. There is no automatic photo retry, image persistence or duplicate-replay protocol. Version 0.2 remembers the explicitly selected device and retries the connection; retake an unconfirmed photo after reconnection.

## Distribution and what “tiny app” means

Normal users should receive a signed Android APK/store app and a prebuilt Windows executable/installer. They should not need Android Studio, Java, Gradle, .NET SDK, ADB, a cable, admin setup of COM ports, or a developer account. **Building source is a separate developer activity.** A self-contained .NET publish bundles its runtime; that makes installation simple but the download is not necessarily tiny. Build x64 and ARM64 separately. Do not trim WinRT/WinForms reflection-dependent code without testing. [Self-contained single-file publishing](https://learn.microsoft.com/en-us/dotnet/core/deploying/single-file/overview).

For Windows public distribution, use Authenticode signing for direct downloads or evaluate Store/MSIX. New signed applications can still encounter reputation checks. Self-signed MSIX adds a certificate-trust step, so it is not the proposed beginner-friendly default. Signing and Store publication are release work, not solved by compiling. [Microsoft signing/reputation guidance](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation), [MSIX signing](https://learn.microsoft.com/en-us/windows/msix/package/sign-msix-package-guide).

Android APKs must be signed; a debug APK is a test artifact with a development key, not a public release. Store distribution uses an app bundle; direct APK installs require source-specific installation permission. Keep release signing keys private and stable for upgrades. [Android signing](https://developer.android.com/studio/publish/app-signing), [Alternative distribution](https://developer.android.com/distribute/marketing-tools/alternative-distribution).

As of this research date, Android developer verification is changing distribution: Google's FAQ distinguishes initial participating-store/regional enforcement from direct sideloading, and recommends preparing for broader 2027 rollout. Public distribution must recheck those requirements; do not promise anonymous, frictionless APK installation forever. This concerns publishers and OS installation, not an account inside this utility. [Developer verification FAQ](https://developer.android.com/developer-verification/guides/faq).

The POC targets .NET 8 and its known WinRT projection, with SDK 8.0.426 selected through `global.json` so self-contained builds bundle runtime 8.0.32 (Microsoft's release metadata lists it as the current runtime, released 13 October 2026). Android uses SDK 35/AGP 8.7.3 with JDK 17/Gradle 8.9. These are deliberate experiment pins, not a claim they are the latest release stack. Before public release, move to a then-supported .NET LTS and recheck Play target-SDK and developer verification rules. [Microsoft release metadata](https://builds.dotnet.microsoft.com/dotnet/release-metadata/8.0/releases.json), [AGP version compatibility](https://developer.android.com/build/releases/agp-8-7-0-release-notes).

## Staged go/no-go tests

1. **Clipboard first:** use Windows “Test clipboard with local JPEG”; paste into Paint, then an unsent ChatGPT draft. Confirm actual attached image, orientation and readable small handwriting. Never press Send as part of this test. Stop if the intended destination does not accept the image format.
2. **Radio baseline:** pair with matching codes in OS settings. With Wi-Fi and mobile data off, manually send a known photo via Android Share → Bluetooth → Windows Receive files. Record size/time. This checks available Classic hardware and provides a comparison without custom app assumptions.
3. **Custom service:** run this POC; select each paired peer once, Android Connect to this laptop, Windows Connect, take and confirm a photo. Require acknowledgement and matching readable pasted image. This tests SDP visibility, unpackaged WinRT consent, and secure cross-platform RFCOMM. On later version 0.2 sessions, open both apps and require automatic reconnection.
4. **Quality and timing:** 20 notebook photos including fine pencil, dense writing, portrait/landscape. Record raw/compressed size when available, preparation, transfer/ack, and overall time. Apply the latency/legibility gates above. Check at desk range and in the union's radio conditions. If it is slow, try a smaller readable JPEG before investigating hotspot TCP; do not build a BLE workaround.
5. **Failures:** deny permission; select the wrong paired device; turn either radio off during a photo; cancel camera; close either app; lock/reopen phone; leave range; disconnect and restart; contend for clipboard. No “Copied” status after a known failed copy. A lost acknowledgement can make the phone report failure after Windows actually copied; retaking can duplicate an image, which must be disclosed.
6. **Release gate:** only after acceptable hardware results, make signed release builds, update the toolchain, test on a clean Windows machine with no .NET runtime and a phone with no developer mode, then test several OEM cameras/adapters and repeat with internet/Wi-Fi off. Confirm no network connection is needed after installation. Setup downloads and store installs themselves may need internet.

The user's initial trial demonstrates the basic hardware path and acceptable subjective speed. Broader reliability and the version 0.2 connection changes still require testing. The next decision should come from that hardware feedback, not another transport layer.
